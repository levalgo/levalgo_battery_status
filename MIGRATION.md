# Migration notes

This repository exists to carry out two native-iOS migrations and keep each
one readable on its own. The code is small on purpose; the value is in the
diffs.

| Tag      | State                   | Diff                                                                                     |
| -------- | ----------------------- | ---------------------------------------------------------------------------------------- |
| `v0.1.0` | Objective-C + CocoaPods | the starting point                                                                         |
| `v0.2.0` | Swift + CocoaPods       | [`v0.1.0...v0.2.0`](https://github.com/levalgo/levalgo_battery_status/compare/v0.1.0...v0.2.0) |

The rule the repository follows is one migration per diff. Mixing the Swift
rewrite with a directory restructure would make both unreadable, so the move
to Swift Package Manager gets its own tag and touches nothing else.

# Part 1 — Objective-C to Swift

`v0.1.0` → `v0.2.0`. The Dart API does not change: anyone already depending on
`0.1.0` upgrades without touching a line.

## What the podspec had to say about it

```ruby
# v0.1.0
s.source_files        = 'Classes/**/*.{h,m}'
s.public_header_files = 'Classes/**/*.h'

# v0.2.0
s.source_files  = 'Classes/**/*.swift'
s.swift_version = '5.0'
```

Three things happen here.

`source_files` stops matching `.h` and `.m`. Obvious, but worth saying that
CocoaPods compiles whatever this glob matches — a stale glob silently ships a
pod with no sources, and the failure surfaces as a missing symbol at link
time, not as a build error in your own file.

`public_header_files` **disappears entirely**. This is the interesting one.
In Objective-C, that key is what makes `LevalgoBatteryStatusPlugin.h` visible
to code outside the pod — specifically to the generated registrant, which
imports it as `<levalgo_battery_status/LevalgoBatteryStatusPlugin.h>`. Swift
has no headers to publish: the compiler generates the module interface from
the source, and `public` is what decides visibility. The declaration moves
from the build system into the language.

`swift_version` comes back. It was in the template, removed when the plugin
went to Objective-C, and returns now.

`DEFINES_MODULE => 'YES'` stays in both. It is what makes the pod a module in
the first place, which is what allows `import levalgo_battery_status` from the
test target.

## Why the Swift class must be `public` **and** `NSObject`-derived

This is the part worth being able to explain rather than recite.

`GeneratedPluginRegistrant.m` is generated by Flutter, in Objective-C, and it
does this:

```objc
[LevalgoBatteryStatusPlugin registerWithRegistrar:
    [registry registrarForPlugin:@"LevalgoBatteryStatusPlugin"]];
```

For that message to reach a Swift class, two independent conditions must both
hold:

**`NSObject`** — Objective-C dispatches by sending messages to objects looked
up in its runtime. Only Swift classes that inherit from `NSObject` are
registered there. A plain Swift class is invisible to `objc_getClass`, so the
registrant cannot find it, even though the symbol exists in the binary.

**`public`** — the registrant is compiled into the *application's* module, not
the plugin's. Swift's default access level is `internal`, which stops at the
module boundary. An `internal` class is fine for Swift inside the pod and
unreachable from the app.

```swift
public class LevalgoBatteryStatusPlugin: NSObject, FlutterPlugin, ... {
  public static func register(with registrar: FlutterPluginRegistrar) { ... }
}
```

Because the class derives from `NSObject`, Swift exposes `register(with:)` to
Objective-C as `registerWithRegistrar:` automatically — the selector the
registrant sends. No `@objc` annotation is needed on the method; the
inheritance is what does it.

Drop either condition and **the project still compiles**. It fails at runtime,
surfacing on the Dart side as `MissingPluginException` — an error that points
at the channel, not at the class visibility that actually caused it. That
indirection is why this is a well-known trap.

## What replaced the header, and what nullability bought

The Objective-C version declared its interface in a separate file:

```objc
NS_ASSUME_NONNULL_BEGIN

@interface LevalgoBatteryStatusPlugin
    : NSObject <FlutterPlugin, FlutterStreamHandler>
@end

NS_ASSUME_NONNULL_END
```

`NS_ASSUME_NONNULL_BEGIN`/`END` marks every pointer in between as non-null
unless it says otherwise. That is not documentation. It is what lets the
compiler bridge the header into Swift as `Plugin` rather than `Plugin?` — and
by extension it is why a half-annotated Objective-C codebase produces Swift
interfaces full of implicitly-unwrapped optionals. Annotating headers is the
cheapest thing a team can do before a Swift migration, and it pays off in the
generated interface rather than in the Objective-C itself.

In Swift the whole file goes away. Optionality is in the type system, so
there is nothing left to assert.

## How the observer teardown changed shape

Both versions register a block-based `NSNotificationCenter` observer, and both
have to unregister it. The difference is what the language does for you.

```objc
// v0.1.0 — the token has to be stored, or you cannot unregister
_batteryStateObserver = [NSNotificationCenter.defaultCenter
    addObserverForName:UIDeviceBatteryStateDidChangeNotification
                object:nil
                 queue:NSOperationQueue.mainQueue
            usingBlock:^(__unused NSNotification *note) {
              [weakSelf emitCurrentState];
            }];
```

```swift
// v0.2.0 — same shape, but `guard let` makes the nil case unmissable
observer = notificationCenter.addObserver(
  forName: UIDevice.batteryStateDidChangeNotification,
  object: nil,
  queue: .main
) { [weak self] _ in
  self?.emitCurrentState()
}
```

The `__weak self` / `[weak self]` capture is the same idea in both: the
notification center retains the block, and the block would retain the plugin,
so without it the plugin never deallocates.

The sharper difference is at the emit site:

```objc
// Objective-C: this check is mandatory
if (_eventSink == nil) { return; }
_eventSink([self currentStateIdentifier]);
```

```swift
// Swift: the language makes it impossible to forget
eventSink?(currentStateIdentifier())
```

Sending a *message* to `nil` in Objective-C is a harmless no-op — which is
exactly why people get complacent. Invoking a *block* that is `nil` is not: it
jumps to address zero and kills the process. The two look alike and behave
completely differently, and that asymmetry is one of the better arguments for
the migration.

## The design change, which matters more than the language

The Objective-C version read `UIDevice` directly. That is fine, and it is also
untestable: `UIDevice.currentDevice.batteryLevel` returns `-1.0` on the
simulator no matter what you do, so there was no way to assert on real
behaviour without a physical device in the loop.

`v0.2.0` puts a protocol at that boundary:

```swift
public protocol BatteryProviding {
  var level: Float { get }
  var state: UIDevice.BatteryState { get }
  func enableMonitoring()
}

public struct DeviceBattery: BatteryProviding { /* wraps UIDevice.current */ }
```

and takes it through the initializer:

```swift
public init(
  battery: BatteryProviding = DeviceBattery(),
  notificationCenter: NotificationCenter = .default
)
```

The default argument is what keeps this free at the call site: production code
still writes `LevalgoBatteryStatusPlugin()` and gets the real device. Tests
pass a stub.

`NotificationCenter` is injected for the same reason but a different problem:
tests that post to `NotificationCenter.default` can see each other's
notifications, and the system's. Each test gets its own instance instead.

## What the tests can do now

Ten XCTest cases, all running on the simulator, none needing hardware:

```swift
final class StubBattery: BatteryProviding {
  var level: Float
  var state: UIDevice.BatteryState
  private(set) var monitoringEnabled = false
  func enableMonitoring() { monitoringEnabled = true }
}
```

That covers percentage rounding, the `UNAVAILABLE` error path, the translation
of all four battery states, the not-implemented method, emission when the
notification fires, silence after `onCancel`, and subscribing twice not
duplicating events.

Two details in the test target are deliberate:

The module is imported **without `@testable`**. The tests therefore exercise
the same public surface the generated registrant sees. If something stopped
being `public`, the tests would stop compiling — which turns the visibility
rule from the previous section into something the build enforces.

The stub is a `class`, not a `struct`, so a test can change `battery.state`
mid-test and then post a notification, and assert that the plugin re-reads the
value. That mirrors the real contract: the notification announces that
something changed, it does not carry the new value.

# What's next

**Part 2 — CocoaPods to Swift Package Manager.** The plugin will support both
at once: Flutter's guidance is explicit that plugins dropping CocoaPods break
apps that have not migrated, and plugins without SPM support break the ones
that have. That means a directory restructure under `ios/`, a `Package.swift`,
and a podspec pointing at the new paths — and verifying both dependency
managers still build.

It also raises the Flutter floor, because the `FlutterFramework` package
dependency requires 3.41 or later.

The CocoaPods trunk registry goes read-only on **December 2, 2026**, which is
what turns this from a nice-to-have into a scheduled piece of work for anyone
shipping a Flutter plugin.
